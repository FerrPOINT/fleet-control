## P2: Oversized Managed Target

Confirmed baseline path: `UpdateAgentConfigRequest::input_errors` accepts a
262145-byte ASCII SOUL. `configuration_files` returns those bytes without a size
check. Config18 saved the target, stopped the original generation and wrote it;
`read_managed` then rejected it at262144 bytes. Rollback calls the same reader
before restoring previous bytes, so it failed too. This is a real source defect,
not a failed native acceptance result.

The successor validates every rendered managed file against the same262144-byte
readback constant, including SOUL, pretty serialized `config.yaml`, expanded and
escaped `.env` secrets, skill content and the generated revision marker. Removal
entries remain explicit absence. It also validates previous bytes and the entire
serialized private plan against its existing1MiB readback bound. Validation runs
before sealing any plan/recipe, PG activation claim or stop permit, and again
before a resumed `planned` record can authorize original stop. Native/physical
observations do not change configuration or grant a new delivery permit.

Regressions added to `runtime::container_activation::tests::`:

- `managed_limits_cover_all_rendered_bytes_and_the_serialized_plan`: demonstrates
  valid oversized API input, all five managed file classes, inclusive262144 and
  rejected262145 bounds, UTF-8 byte rather than character accounting, and a plan
  too large to read even though its individual files fit.
- `oversized_target_never_seals_or_changes_previous_working_bytes`: real Linux
  private-file boundary readback plus rejection by the production sealer; no
  plan/recipes are written and exact previous working bytes remain unchanged.

An invalid target remains drained; this patch does not invent a generic Docker
finisher or release drain without proof. It does not retroactively repair a
previously applied oversized target or authorize deletion/replacement of sealed
evidence. Such existing custody needs separate reviewed recovery.

## P2: Lost Pre-Plan Retry

Confirmed baseline path: the config queue sets `claimed_at` before invoking
config18. Original physical observe/endpoint or authenticated health can fail
before the private plan/PG activation record exists. The worker then ended;
`claimed_at IS NULL` excludes the revision from new claims and pending lookup
selects only existing activation records. A transient failure thus stranded the
otherwise eligible revision for the lifetime of that custodian.

The live worker now retains that exact claimed revision across read-only plan
failures, with a five-second delay between attempts. Each attempt releases its
per-agent operation and OS locks before waiting, then freshly reacquires them
and repeats the original owner, PG record and private-path checks. No queue claim
is cleared/reissued and no Base prepare/start/stop permit is generated by retry.

The retry tag has exactly one production admission point: a failure from the
read-only `activation_plan` builder, after proof of no PG activation record and
an explicit `NotFound` for its private plan. The builder no longer writes recipes.
Only existing Base169 observe/endpoint/resolve and authenticated GET readiness
are used there. Base `read_registered` opens SQLite with `mode=ro`; mount resolve
uses inventory/readback only. Native mutation begins only after successful plan
sealing and the existing durable PG phase permits.

All errors outside this explicitly read-only stage default to held, including
unknown/partial sealing, PG claim ACK, stop, prepare, attach, start and publication.
Existing private plans, inaccessible paths, foreign custody and unknown effects
are not re-planned. Original record readback and all unit16/17/18 guards remain.
Explicit rendered-byte/plan validation failures do not loop. Persistent
observation mismatch can keep retrying read-only checks while drained, but can
never relax the underlying guard.

Regressions added:

- `read_only_observe_failure_retries_original_command_until_recovery`: invokes the
  actual sealed Python adapter with a fake original-registration source, first
  returning held and then the exact running snapshot. Audit must contain exactly
  two original observe calls, no lifecycle commands or native journal creation.
- `validation_and_unknown_effect_failures_never_retry`: validates the explicit
  error classification and one-attempt hold for every non-read-only stage.

This retry is limited to the current live custodian. It does not add process-
restart adoption, recovered-owner activation or a new persistence contract.
Discovery failures before no-record/no-plan proof still hold; loss of that live
worker before sealing is not automatically reclaimed. These limitations are
not native acceptance or production runtime readiness.
